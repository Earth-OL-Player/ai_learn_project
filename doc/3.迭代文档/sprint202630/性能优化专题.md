## 1. 结论先行

按当前部署条件看，真正的短板不是 CPU 或内存，而是 **5Mbps 公网带宽、静态大图、未显式收紧的 Java 并发池、缺少面向现有 SQL 的组合索引、Python 每次重复构造模型和 Agent**。

上线前最高收益的优化顺序如下：

1. 先做 Nginx 静态资源强缓存、gzip、上游 keepalive。
2. 立即压缩 `rank-characters` 角色 PNG 和学习路线 PNG，并保持懒加载。
3. 显式限制 Java Tomcat、Hikari、AI 流式线程池和 Uvicorn 并发。
4. 新增匹配现有 SQL 的 Flyway 索引迁移。
5. 给 Python `init_chat_model` 和 `create_agent` 加配置指纹驱动的小容量缓存。
6. 给 Java 低变更频率配置和分类数据加本地短 TTL 缓存。
7. 收敛日志、普通 API 超时、导出和深分页风险。

本专题没有建议新增 Redis、Qdrant、自建 MySQL 或新服务器；因此本次不需要新增 `doc/中间件/` 文档。

## 4. 第 1 位：Nginx 静态资源强缓存、gzip、上游 keepalive

### 4.1 当前证据

部署文档中已有 Nginx 反代 Java 后端和 SSE 禁缓冲配置：

- Java 后端通过 `127.0.0.1:8080` 暴露给 Nginx。
- Python AI 服务只被 Java 后端访问，监听 `127.0.0.1:8000`。
- SSE 路径已经设置 `proxy_buffering off` 和较长超时。
- 普通 `/api/` 使用 `proxy_read_timeout 120s`。
- 未看到 `/assets/`、`/rank-characters/`、图片、CSS、JS 的强缓存配置。
- 未看到 gzip 或 Brotli 的明确启用片段。

### 4.2 推荐方案

在宝塔站点 Nginx 配置中补充静态资源缓存。`/assets/` 是 Vite 带 hash 的构建产物，适合强缓存；`index.html` 不能强缓存，否则发布后用户可能继续加载旧入口文件。

```nginx
# Vite 构建产物文件名带 hash，适合长期缓存。
location ^~ /assets/ {
    try_files $uri =404;
    expires 30d;
    add_header Cache-Control "public, max-age=2592000, immutable";
    access_log off;
}

# 段位角色图体积较大，必须减少重复下载。
location ^~ /rank-characters/ {
    try_files $uri =404;
    expires 30d;
    add_header Cache-Control "public, max-age=2592000";
    access_log off;
}

# 入口文件必须保持可更新，避免发布后命中旧入口。
location = /index.html {
    add_header Cache-Control "no-cache";
    try_files $uri =404;
}

# Vue Router 兜底入口。
location / {
    try_files $uri $uri/ /index.html;
}
```

全局 gzip 建议保持中等压缩等级，优先减小公网传输体积，不追求极限压缩。

```nginx
gzip on;
gzip_comp_level 5;
gzip_min_length 1024;
gzip_vary on;
gzip_types
    text/plain
    text/css
    text/javascript
    application/javascript
    application/json
    application/xml
    image/svg+xml;
```

Nginx 到 Java 后端建议使用 upstream keepalive，降低本机反代短连接开销。

```nginx
upstream ai_learn_backend {
    server 127.0.0.1:8080;
    keepalive 32;
}

location /api/ {
    proxy_pass http://ai_learn_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 60s;
    proxy_send_timeout 60s;
}
```

SSE 路径继续单独配置，不要套用普通接口的 60s 超时和缓冲。

```nginx
location /api/v1/practice/messages/stream {
    proxy_pass http://ai_learn_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
```

### 4.3 宝塔 Nginx 一键覆盖配置

当前线上配置已经包含宝塔证书验证、扩展 include、PHP 引用、伪静态 include、SSE 流式接口、普通 API 反代、Vue Router 兜底和敏感文件拦截。优化时必须保留这些能力，只补充静态资源强缓存、gzip 和 upstream keepalive。

修改前关键差异：

```nginx
# 后端反代直接写 127.0.0.1:8080，没有 upstream keepalive。

# 图片缓存不包含 webp，rank-characters 已改成 webp 后不会命中这条。

    error_log /dev/null;
    access_log /dev/null;
}

# js/css 只缓存 12h，没有单独给 Vite /assets hash 资源 immutable 强缓存。
location ~ .*\.(js|css)?$
{
    expires      12h;
    error_log /dev/null;
    access_log /dev/null;
}
```

### 4.4 为什么提升性能

5Mbps 公网带宽理论上限约 0.625MB/s，实际还要扣除 TLS、HTTP 和网络抖动。缓存命中后，重复访问不再下载大部分 JS、CSS、图片；gzip 后 JS/CSS/JSON 在首访时也能明显变小。upstream keepalive 虽然不是最大瓶颈，但成本很低，可以减少 Nginx 到 Java 的连接建立开销。

### 4.5 代价和副作用

- `index.html` 如果误设 `immutable`，发布新版本后用户可能加载旧 JS 入口，出现白屏或接口不匹配。
- `/rank-characters/` 图片文件名目前不带 hash，如果替换同名图片，浏览器可能继续使用旧图 30 天。解决方式是文件名带版本号，或上线替换时短暂降低缓存时间。
- gzip 对已经压缩过的 PNG/WebP/JPEG 几乎无收益，不应强行压缩图片。
- Brotli 比 gzip 更省流量，但如果宝塔 Nginx 没有模块，不建议上线前临时编译 Nginx。

### 4.6 验收方式

```powershell
curl -I https://<域名占位符>/assets/index.js
curl -I https://<域名占位符>/rank-characters/realwoman/female_lv001-010_lianqi.webp
curl -I https://<域名占位符>/index.html
curl -H "Accept-Encoding: gzip" -I https://<域名占位符>/assets/index.css
```

验收标准：

- `/assets/` 返回 `Cache-Control: public` 且有较长 `max-age`。
- `/rank-characters/` 返回缓存头，且 Nginx 访问日志不再记录每次图片请求。
- `/index.html` 返回 `Cache-Control: no-cache`。
- CSS/JS 响应包含 `Content-Encoding: gzip`。
- AI 流式接口仍能逐字或分片返回，不能被 Nginx 缓冲到最后一次性输出。

### 6.4 为什么提升性能

### 6.5 代价和副作用

- AI 流式 `max=4` 会降低同时服务 AI 长连接的能力，但配合单用户并发限制更符合当前 MVP。
- Uvicorn `--limit-concurrency 32` 会让异常高并发更早得到 503 或排队，不会无限堆积内存。
- `--no-access-log` 会减少日志量，但排查请求明细时需要依赖应用日志和 Nginx 日志。

CREATE INDEX idx_comments_deleted_parent_created_id

### 7.4 代价和副作用

- `%keyword%` 这种前缀通配搜索无法充分利用普通 BTree 索引，索引只能优化无 keyword 或弱 keyword 的默认列表路径。

## 8. 第 5 位：Python 模型和 Agent 构造结果缓存

### 8.1 当前证据

`ai-service/app/practice/model_factory.py` 当前每次请求都会：

- `chat_model()` 调用 `init_chat_model(...)`。
- `grading_agent()` 调用 `create_agent(..., response_format=PracticeGradeEvaluation)`。
- `discussion_agent()` 调用 `create_agent(...)`。

这些对象和模型配置强相关，且配置变化频率低，适合小容量缓存。

### 8.2 推荐方案：配置内容指纹驱动缓存

给工厂增加模型缓存键，并对聊天模型、评分 Agent、讨论 Agent 使用小容量 LRU 缓存。缓存键不能只用 `ModelLevel`、配置 id 或模型名称，必须由本次请求真正传给 Python 的模型调用参数生成，否则后台更新同一档模型后仍会命中旧对象。

当前 Java 已经在 `PracticeAiClient.appendModelConfig` 中把 `model`、`baseUrl`、`apiKey` 放进请求级 `modelConfig`。建议再补充一个不含敏感信息的 `configFingerprint` 字段，由 Java 根据 `modelName`、规整后的 `baseUrl`、`apiKey` 摘要、`updatedAt` 生成。即使主动清理通知失败，只要下一次请求携带了新配置或新指纹，Python 也会自然避开旧缓存。

```python
from collections import OrderedDict
from dataclasses import dataclass
from hashlib import sha256
from threading import RLock
from typing import Any, Callable


CACHE_LIMIT = 16


@dataclass(frozen=True)
class ModelCacheKey:
    """模型和 Agent 缓存键，避免把原始密钥放进 key 或日志。"""

    provider: str
    model: str
    base_url: str
    api_key_hash: str
    timeout_seconds: int
    max_output_tokens: int
    config_fingerprint: str


class PracticeModelFactory:
    """创建刷题场景所需的 LangChain 模型和 Agent。"""

    def __init__(self, provider_adapter: PracticeProviderAdapter) -> None:
        """初始化模型工厂依赖和小容量缓存。"""
        self._provider_adapter = provider_adapter
        self._cache_lock = RLock()
        self._chat_models: OrderedDict[ModelCacheKey, Any] = OrderedDict()
        self._grading_agents: OrderedDict[ModelCacheKey, Any] = OrderedDict()
        self._discussion_agents: OrderedDict[ModelCacheKey, Any] = OrderedDict()

    def grading_agent(self, model_config: PracticeModelConfig | None = None) -> Any:
        """获取答案评分 Agent，配置变化后自动换用新缓存键。"""
        key = self._cache_key(model_config)
        return self._get_or_create(self._grading_agents, key, lambda: create_agent(
            model=self.chat_model(model_config),
            tools=[],
            system_prompt=GRADE_SYSTEM_PROMPT,
            response_format=PracticeGradeEvaluation,
        ))

    def discussion_agent(self, model_config: PracticeModelConfig | None = None) -> Any:
        """获取本题讨论 Agent，配置变化后自动换用新缓存键。"""
        key = self._cache_key(model_config)
        return self._get_or_create(self._discussion_agents, key, lambda: create_agent(
            model=self.chat_model(model_config),
            tools=[],
            system_prompt=DISCUSSION_SYSTEM_PROMPT,
        ))

    def chat_model(self, model_config: PracticeModelConfig | None = None) -> Any:
        """获取聊天模型，配置变化后自动换用新缓存键。"""
        key = self._cache_key(model_config)
        return self._get_or_create(self._chat_models, key, lambda: init_chat_model(
            self._provider_adapter.model_name(model_config),
            **self._provider_adapter.chat_model_kwargs(model_config),
        ))

    def clear_cached_objects(self) -> None:
        """清理模型和 Agent 构造缓存，用于后台保存配置后的主动失效。"""
        with self._cache_lock:
            self._chat_models.clear()
            self._grading_agents.clear()
            self._discussion_agents.clear()

    def _cache_key(self, model_config: PracticeModelConfig | None) -> ModelCacheKey:
        """生成不会泄露密钥的配置内容指纹。"""
        kwargs = self._provider_adapter.chat_model_kwargs(model_config)
        api_key = self._provider_adapter.api_key(model_config)
        config_fingerprint = getattr(model_config, "configFingerprint", "") if model_config else ""

        # 后台配置内容变化后，api_key_hash 或 config_fingerprint 必须变化。
        return ModelCacheKey(
            provider=self._provider_adapter.model_provider(),
            model=self._provider_adapter.model_name(model_config),
            base_url=self._provider_adapter.normalized_base_url(model_config),
            api_key_hash=sha256(api_key.encode("utf-8")).hexdigest(),
            timeout_seconds=int(kwargs.get("timeout") or 0),
            max_output_tokens=int(kwargs.get("max_completion_tokens") or 0),
            config_fingerprint=config_fingerprint.strip(),
        )

    def _get_or_create(
            self,
            cache: OrderedDict[ModelCacheKey, Any],
            key: ModelCacheKey,
            builder: Callable[[], Any]) -> Any:
        """从小容量 LRU 缓存读取对象，不存在时再构造。"""
        with self._cache_lock:
            cached = cache.get(key)
            if cached is not None:
                cache.move_to_end(key)
                return cached

            # 当前缓存只保留少量模型变体，避免长期持有旧客户端。
            created = builder()
            cache[key] = created
            if len(cache) > CACHE_LIMIT:
                cache.popitem(last=False)
            return created
```

如果后续新增 `temperature`、`timeout`、`max_tokens`、`model_provider` 等可配置字段，也必须同步纳入 `ModelCacheKey` 和 Java 侧 `configFingerprint`。不要用 TTL 解决配置一致性，TTL 只能作为异常兜底，不能作为后台保存后立即生效的主机制。

### 8.3 配置变更立即生效策略

后台保存模型配置时，需要把“使用新配置”和“释放旧对象”拆开处理：

1. `ModelEntitlementService.saveAdminModelConfig(...)` 写入 `model_configs` 后，重新查询保存后的记录，生成不含明文 API Key 的 `configFingerprint`。
2. 如果第 6 位优化落地了 Java 本地模型配置缓存，保存成功后必须立即按 `ModelLevel` 主动失效，不能等 30 秒到 1 分钟 TTL。
3. `PracticeAiClient.appendModelConfig(...)` 在 `modelConfig` 中追加 `configFingerprint`。Python 收到新请求后，缓存键变化，下一次评分或讨论会构造新模型和新 Agent。
4. Java 后台保存成功后，调用 AI 服务内部接口，例如 `POST /internal/model-cache/invalidate`，Python 侧执行 `PracticeModelFactory.clear_cached_objects()`。当前单机部署直接全量清理即可，容量只有 16，不需要做复杂的按等级局部淘汰。
5. 内部清理接口必须只允许后端调用，可以使用内网地址加共享管理密钥，密钥使用环境变量配置，文档和示例里只能放占位符。
6. 主动清理接口调用失败时，Java 只记录 `WARN`，不要回滚模型配置保存。正确性由请求级新 `modelConfig` 和新缓存键保证，清理失败只会让旧对象多占用一段内存。

这个策略的生效边界是：后台保存接口返回成功之后发起的新 AI 请求必须使用新配置；保存动作之前已经进入 Python 执行中的请求允许继续用旧配置完成，不强行中断流式输出。

### 8.4 为什么提升性能

AI 调用的主要耗时仍在外部模型响应，但 LangChain 模型包装和 Agent 图构造也有固定开销。缓存后，每次请求可减少重复对象构造、提示词装配和内部运行时初始化成本，尤其对短回复、流式首 token 和本地规则兜底路径更明显。

### 8.5 代价和副作用

- 不能只按模型等级或配置 id 缓存，否则同一档模型配置更新后仍可能命中旧 Agent。
- 后台保存后已经在途的 AI 请求不会切换配置，只保证保存成功后的新请求立即使用新配置。
- Python 主动失效接口会增加一个内部管理端点，需要管理密钥和内网访问控制，避免暴露给公网。
- 主动失效失败不能影响后台保存结果，旧对象最多等待 LRU 淘汰，不允许依赖重启 AI 服务解决一致性。
- 缓存容量过大会占内存，尤其是不同模型供应商对象内部持有连接池或客户端时。
- 如果把 API Key 直接作为缓存 key 或日志字段，调试时容易泄露敏感信息。必须只使用哈希摘要，不输出原文。
- 某些第三方客户端如果不是线程安全对象，需要先确认 LangChain 当前对象是否可并发复用；不确定时先只缓存配置解析结果或底层 chat model。

### 8.6 验收方式

上线前记录相同请求的耗时：

- AI 服务日志中的首 token 时间。
- Java `AI 调用观测` 日志中的 `durationMs` 和 `firstTokenMs`。
- Python 进程内存是否持续增长。
- 后台保存模型配置后下一次请求携带的 `configFingerprint` 是否变化。

验收标准：

- 同一模型配置重复调用时，首 token 时间或总耗时有可观察下降。
- 修改模型配置后，不重启 AI 服务、不手工清缓存，后台保存成功后的下一次 AI 请求立即使用新配置。
- Python 主动失效接口调用失败时，新请求仍因缓存键变化而使用新配置，只允许出现旧对象短暂占用内存。
- 日志中不出现 API Key、真实模型密钥或完整敏感请求体。

## 9. 第 6 位：Java 本地短 TTL 缓存

### 9.1 适合缓存的数据

当前项目是单机部署，且 README 已说明 Redis 没有接入运行代码。上线前优先使用本地短 TTL 缓存，而不是临时引入 Redis。

适合缓存：

- 题目类型列表。
- 系统设置，例如用户上限、默认配置。
- 模型配置 `model_configs`。
- 徽章规则和成长等级静态规则。
- 首页或个人中心中低频变化的统计摘要。

不适合缓存：

- 用户登录态和权限判断。
- AI 单用户并发租约。
- 点赞、评论、兑换码使用这类强一致写入链路。
- 高频变更且用户需要立即看到的个人资料。

### 9.2 推荐方案

使用 Java 内存缓存即可，可以是简单的 `ConcurrentHashMap + expireAt`，也可以使用轻量 Caffeine。若新增依赖，需要评估依赖体积和维护成本；上线前更推荐先写少量本地缓存工具，范围控制在几个 service 内。

建议 TTL：

| 数据 | TTL | 失效策略 |
| --- | --- | --- |
| 题目类型列表 | 5 分钟 | 题库导入、清空、编辑后主动失效 |
| 系统设置 | 1 分钟 | 管理后台保存后主动失效 |
| 模型配置 | 最多 1 分钟兜底 | 管理后台保存后立即主动失效，并同步生成新的 `configFingerprint` |
| 徽章规则 | 10 分钟 | 徽章规则变更后主动失效 |

### 9.3 为什么提升性能

低频数据如果每个页面请求都查数据库，会在并发下放大 TDSQL 往返和连接池占用。本地短 TTL 缓存能把这类重复查询从数据库移到进程内存，代价很低。

### 9.4 代价和副作用

- 除模型配置外，其他低频数据在 TTL 内可能读到旧数据；模型配置不允许依赖 TTL，必须靠后台保存后的主动失效和新 `configFingerprint` 立即生效。
- 本地缓存只在单机可靠；以后多实例部署时需要重新设计失效策略。
- 缓存过多会让业务一致性变复杂，所以只缓存低频、可容忍短暂延迟的数据。

### 9.5 验收方式

- 开启 SQL 日志或通过 TDSQL 监控观察低频配置表查询次数下降。
- 后台保存模型配置后确认 Java 缓存立即失效，下一次 AI 请求携带新的 `configFingerprint`。
- TTL 到期后确认能重新加载数据库新值。

## 10. 第 7 位：日志降噪和访问日志关闭

### 10.1 当前证据

- Java `application.yml` root 和业务包默认 INFO。
- Python `ai-service` 当前 HTTP middleware 每个请求进入和结束都打印 INFO。
- `llm_logger.py` 已经做到 DEBUG 才记录完整 prompt/response，INFO 只记录长度、耗时和 token。
- 流式 chunk 日志已经只记录第 1 个和每 50 个 chunk，方向正确。
- Uvicorn systemd 当前未看到 `--no-access-log`。

### 10.2 推荐方案

生产保持：

```env
LOGGING_LEVEL_ROOT=INFO
AI_SERVICE_LOG_LEVEL=INFO
```

Uvicorn 使用：

```ini
--no-access-log
```

Nginx 对静态资源关闭访问日志：

```nginx
location ^~ /assets/ {
    access_log off;
}

location ^~ /rank-characters/ {
    access_log off;
}
```

### 10.3 为什么提升性能

日志不是当前最大瓶颈，但流式 AI、图片、静态资源和后台列表会产生大量请求。减少无价值访问日志能降低磁盘 IO、日志切割压力和字符串格式化开销，也能让真正的错误更容易被发现。

### 10.4 代价和副作用

- 关闭 Uvicorn access log 后，排查 Python 每个请求的原始访问明细会少一层来源。
- 生产不开 DEBUG 后，无法直接看到完整 prompt 和模型响应，需要临时调级排查。
- 静态资源不打 access log 后，无法从 Nginx 日志直接统计每张图片访问量，需要依赖 CDN 或 Web 分析工具。

### 10.5 验收方式

- 连续刷新页面，确认静态资源不再刷 Nginx access log。
- AI 请求仍能看到 traceId、耗时、状态、token 等关键观测日志。
- 临时调 DEBUG 后可排查问题，完成后能恢复 INFO。

## 11. 第 8 位：普通 API 超时收敛，流式接口单独保留长超时

### 11.1 当前证据

- Nginx 普通 `/api/` 当前示例为 `proxy_read_timeout 120s`。
- SSE 当前示例为 `proxy_read_timeout 300s`，这是合理的。
- Java AI 客户端默认 `AI_SERVICE_TIMEOUT_SECONDS=15`。
- Python 模型调用默认 `ai_grading_timeout_seconds=20`。
- Java `PracticeController` SSE timeout 为 120000ms。

### 11.2 推荐方案

普通 API：

- Nginx `proxy_read_timeout` 和 `proxy_send_timeout` 收敛到 60s。
- 后台导入、导出等潜在慢接口通过行数限制和任务拆分解决，不靠无限加超时。

AI 流式：

- SSE Nginx 继续保持 300s。
- Java `SseEmitter` 120s 可以先保持，结合模型真实响应再调。
- Python 评分 timeout 20s 可保持，讨论流式依赖客户端断开处理。

### 11.3 为什么提升性能

异常慢请求如果长时间占用连接，会挤占 Tomcat 线程、Nginx 连接和浏览器等待队列。普通 API 收敛超时后，异常链路更早失败，系统整体尾延迟更稳定。

### 11.4 代价和副作用

- 后台导入大 CSV 或兑换码导出如果超过 60s，会更早失败。
- 慢查询不会被超时配置真正修复，只会更快暴露，需要配合索引和分页优化。
- SSE 不能套用普通 API 的 60s，否则长回答可能被中断。

### 11.5 验收方式

- 普通接口 60s 内无响应时能明确失败。
- SSE 长回答超过 60s 时不会被 Nginx 中断。
- Java 和 Python 日志中同一个 traceId 能串起超时原因。

## 12. 第 9 位：导出行数上限和深分页游标化

### 12.1 当前证据

当前后端多处列表使用 `LIMIT #{pageSize} OFFSET #{offset}`。这在小数据下没问题，但数据增长后，深页查询会扫描并丢弃前面大量行。

兑换码导出链路中，`ModelEntitlementService` 遍历 `findRedemptionsForExport(...)` 的全部结果。如果兑换码数量变大，一次导出会同时占用数据库、Java 内存和 HTTP 响应时间。

### 12.2 推荐方案

上线前至少做导出保护：

- 兑换码导出限制最大行数，例如 5000 或 10000。
- 导出前返回总数提示，超出限制要求缩小筛选条件。
- 导出响应使用流式写出，避免一次性构造大字符串。

数据增长后再做游标分页：

- 评论、建议、题库、兑换码列表可用 `(created_at, id)` 游标。
- 用户列表可用 `id` 游标。
- 热门排序可用 `(like_count, created_at, id)` 游标。

### 12.3 为什么提升性能

OFFSET 越大，数据库需要跳过的记录越多。游标分页可以从上次最后一条继续向后扫，避免深页扫描。导出行数上限可以防止管理员一次操作拖慢数据库和 Java 进程。

### 12.4 代价和副作用

- 游标分页不适合“跳到第 100 页”这类交互，前端要改成“加载更多”或“下一页”。
- 导出上限会改变管理员习惯，需要文案提示如何缩小筛选条件。
- 流式导出实现比一次性导出复杂，需要处理客户端中断和异常日志。

## 14. 第 11 位：不建议为了性能临时新增的东西

### 14.1 不建议新增 Redis

原因：

- README 已说明当前运行代码未接入 Redis。
- 当前限流是单机内存级过渡方案。
- 单机 MVP 上线前引入 Redis，会增加部署、监控、备份和故障点。

代价：

- 需要新增中间件文档、环境变量、连接池、异常兜底。
- Redis 故障会影响登录限流、AI 并发租约或缓存链路。
- 当前最值得做的是 Nginx、图片、索引和本地短 TTL 缓存。

### 14.2 不建议恢复 Qdrant 或 RAG

原因：

- 文档已多处说明当前 AI 刷题不依赖 Qdrant。
- 学习资料是静态内容和题库为主，暂时不需要向量检索链路。

代价：

- 新增 Python 依赖、向量库服务、数据同步、索引构建和运维成本。
- 对上线前性能没有直接收益，反而增加内存和部署复杂度。

### 14.3 不建议把 Uvicorn worker 直接加到 2 或 4

原因：

- AI 服务可能持有模型客户端、缓存对象和日志处理器，多 worker 会复制内存。
- Java 后端当前单用户 AI 并发上限为 1，盲目加 worker 不会解决核心瓶颈。

代价：

- 内存上涨，日志倍增。
- 模型供应商限流更容易被打满。
- 本地缓存会按进程复制，配置刷新更复杂。

### 14.4 不建议把 JVM `-Xmx` 调到 4GB

原因：

- 当前 4C8G 同机跑 Nginx、Java、Python 和系统服务。
- Java 已配置 `-Xmx2048m`，更大的堆不一定更快。

代价：

- 挤占 Python AI 服务和系统页缓存。
- GC 暂停可能变长。
- 内存紧张时系统更容易 swap，整体性能反而下降。

### 14.5 不建议生产常开 DEBUG

原因：

- AI prompt、response、参数校验和后台请求会放大日志。
- DEBUG 可能暴露业务内容和用户输入。

代价：

- 磁盘 IO 增加。
- 日志检索更慢。
- 敏感信息泄露风险上升。

## 17. 最终建议

最优先做的不是改业务逻辑，而是先把“公网传输”和“并发上限”管住。当前项目已经有路由懒加载、AI 单用户并发限制、SSE 断开取消、INFO/DEBUG 分层日志等基础，继续投入时应避开大而重的中间件方案，把上线前优化集中在 Nginx、图片、连接池、线程池、索引和小范围缓存上。

本专题只输出性能优化方案，没有新增中间件，也没有新增或修改中间件文档。若后续真正引入 Redis、Qdrant 或其他中间件，必须同步更新 `doc/中间件/`。

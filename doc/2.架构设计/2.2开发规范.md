# AI应用开发学习平台开发规范

版本：v1.1  
日期：2026-05-14  
适用范围：`ai-learn-web`、`ai-learn-backend`、`ai-service`

## 1. 规范目标

本文档把架构设计落到日常开发约定，重点解决四类问题：模块边界不清、接口风格不统一、配置泄露、代码难以维护。

开发优先级：

1. `doc/1.需求文档/1.2需求文档.md`
2. `doc/2.架构设计/2.1架构设计文档.md`
3. `doc/2.架构设计/2.2开发规范.md`
4. `doc/2.架构设计/2.3接口规范.md`
5. `doc/中间件/` 下对应中间件文档

## 3. 后端 DDD 分层规范

后端统一根包为：

```text
com.earth.online.player.ailearn
```

后端采用 DDD 领域驱动设计组织代码，不使用传统 Controller、Service、Mapper 三层作为主结构。整体仍按业务模块拆包，模块内部按 DDD 分层，保证当前单体工程内聚清晰，也方便后续按业务模块拆分微服务。

推荐结构：

```text
com.earth.online.player.ailearn
├── common/                    # 技术通用能力
│   ├── config/                # 通用配置
│   ├── exception/             # 全局异常
│   ├── response/              # 统一响应
│   ├── pagination/            # 分页模型
│   └── trace/                 # traceId 和日志上下文
├── auth/
│   ├── interfaces/            # Controller、Request、Response、Assembler
│   ├── application/           # Command、Query、AppService、UseCase、应用 DTO
│   ├── domain/                # Aggregate、Entity、ValueObject、DomainService、Repository 接口、DomainEvent
│   └── infrastructure/        # Persistence Entity、Mapper、RepositoryImpl、外部 Client、配置
├── user/
│   ├── interfaces/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
├── learning/
├── suggestion/
├── comment/
├── question/
├── answer/
├── growth/
└── agent/
```

各业务模块可按复杂度裁剪子包。简单模块可以先保留必要分层，但不得把核心业务规则直接写进 Controller 或 Mapper。

DDD 分层职责：

| 层 | 职责 | 禁止事项 |
| --- | --- | --- |
| `interfaces` | 处理 HTTP 入参、认证上下文、响应转换；典型对象包括 Controller、Request、Response、Assembler | 禁止写业务规则，禁止直接调用 Mapper，禁止返回持久化实体 |
| `application` | 承载业务用例编排、事务边界、权限协作、跨模块协调；典型对象包括 Command、Query、AppService、UseCase | 禁止沉淀核心领域规则，禁止绕过领域对象直接改数据库 |
| `domain` | 承载核心业务概念和规则；典型对象包括聚合、实体、值对象、领域服务、仓储接口、领域事件 | 禁止依赖 Spring MVC、MyBatis、Redis、Qdrant、外部 HTTP Client 等技术细节 |
| `infrastructure` | 实现持久化、缓存、外部服务调用和技术适配；典型对象包括 Mapper、Persistence Entity、RepositoryImpl、Client、Config | 禁止把持久化对象当领域对象向上泄露，禁止承载核心业务决策 |
| `common` | 放统一响应、异常、分页、traceId、日志脱敏等技术通用能力 | 禁止放具体业务流程和领域规则 |

依赖方向：

```text
interfaces -> application -> domain
infrastructure -> domain
application -> domain
```

说明：

- `domain` 是核心层，不依赖其他业务层和技术框架。
- `application` 通过领域对象和领域仓储接口完成用例编排。
- `infrastructure` 实现领域层定义的仓储接口或外部端口。
- `interfaces` 只做协议适配，把 HTTP 请求转换为应用层命令或查询对象。

强制约束：

- Controller 只能调用应用层用例或 AppService，不得直接调用 Mapper。
- 跨模块访问优先通过对方 application 暴露的用例接口；不得直接使用对方 Mapper、Persistence Entity 或内部领域对象。
- 用户私有资源查询必须在应用层或领域规则中校验 `user_id` 或等价权限条件。
- 写操作事务边界放在 application 层；领域层保持纯业务规则表达。
- Repository 接口定义在 domain 层，实现放在 infrastructure 层。
- MyBatis Mapper、Persistence Entity、Redis 操作、AI 服务 Client 只能放在 infrastructure 层。
- 复杂 SQL 可以使用 MyBatis XML，但 SQL 文件需要保持可读、可测。
- 魔法值抽取为枚举、常量、值对象或配置项。

## 4. 后端命名与代码质量

命名约定：

| 类型 | 命名 |
| --- | --- |
| 请求对象 | `XxxRequest` |
| 响应对象 | `XxxResponse` |
| 分页响应 | `PageResponse<T>` |
| 命令对象 | `XxxCommand` |
| 查询对象 | `XxxQuery` |
| 应用服务 | `XxxAppService` 或 `XxxUseCase` |
| 领域服务 | `XxxDomainService` |
| 聚合根 | `XxxAggregate` |
| 领域实体 | 按业务语义命名，例如 `Question`、`AnswerRecord` |
| 值对象 | 按业务语义命名，必要时使用 `XxxValue` |
| 仓储接口 | `XxxRepository`，放在 `domain` 层 |
| 仓储实现 | `XxxRepositoryImpl`，放在 `infrastructure` 层 |
| 持久化对象 | `XxxPo` 或 `XxxPersistenceEntity`，放在 `infrastructure` 层 |
| Mapper | `XxxMapper`，放在 `infrastructure` 层 |
| 转换器 / 装配器 | `XxxConverter`、`XxxAssembler` |
| 枚举 | `XxxEnum` |

代码要求：

- 业务异常使用统一异常类型，禁止到处抛 `RuntimeException`。
- 错误码和文案集中管理，Controller 不硬编码错误文案。
- 领域对象不添加 MyBatis、JPA、Jackson 等持久化或接口协议注解。
- 持久化对象、接口 DTO、领域对象之间通过 Converter 或 Assembler 转换。
- 复杂方法上方写方法注释，关键业务步骤写简体中文单行注释。
- 注释说明“为什么这样做”，不要重复代码字面意思。
- 方法尽量短小，单一职责，避免深层嵌套。
- 对外 DTO 不暴露密码哈希、内部 Token、模型 Key、完整连接串等敏感字段。

## 5. 数据库与迁移

- 表结构变更必须通过 Flyway migration 管理。
- Migration 命名：`V版本号__说明.sql`，例如 `V1__init_user_tables.sql`。
- 表名使用小写下划线，例如 `answer_records`。
- 字段名使用小写下划线，例如 `created_at`。
- 主键策略在项目初始化时统一确定，避免混用。
- 业务表默认包含 `created_at`、`updated_at`。
- 需要逻辑删除的表增加 `deleted` 或 `deleted_at`。
- JSON 字段只用于结构灵活且不频繁筛选的数据，例如 `ai_feedback`。
- 高频查询字段必须建索引，重点关注 `user_id`、`question_id`、`created_at`、状态字段。
- 生产库禁止手工改表后不沉淀 migration。

## 6. 前端开发

推荐结构：

```text
src/
├── api/                       # 后端 API 封装
├── assets/                    # 静态资源
├── components/                # 通用组件
├── layout/                    # 页面布局
├── pages/                     # 业务页面
├── router/                    # 路由配置和守卫
├── stores/                    # Pinia 状态
├── styles/                    # 全局样式
├── types/                     # TypeScript 类型
└── utils/                     # 工具函数
```

要求：

- 页面组件不直接拼接后端基础地址，统一通过 `api` 模块调用。
- 登录态、用户信息和菜单状态统一放在状态层。
- 路由守卫负责前端登录引导，后端负责最终鉴权。
- 表单校验规则尽量复用，避免页面内重复粘贴。
- TypeScript 开启严格模式后，不为省事大量使用 `any`。
- API 类型与后端接口规范保持一致。
- loading、空状态、错误提示和登录引导要统一组件化。

## 7. AI 服务开发

推荐结构：

```text
ai-service/
├── app/
│   ├── api/                   # FastAPI 路由
│   ├── agent_graph/           # LangGraph 工作流
│   ├── rag/                   # 切分、索引、检索、重排序
│   ├── question_generation/   # 出题能力
│   ├── answer_grading/        # 审题评分能力
│   ├── llm_clients/           # 模型供应商适配
│   ├── prompts/               # 提示词模板
│   ├── schemas/               # Pydantic 请求响应模型
│   └── config/                # 配置加载
├── tests/
├── .env.example
└── README.md
```

要求：

- `ai-service` 只暴露内部接口，不直接给浏览器调用。
- 请求和响应必须使用 Pydantic 模型约束。
- Prompt 模板独立存放，维护版本号或变更说明。
- 模型调用必须设置超时、重试和失败兜底。
- 模型 API Key、内部鉴权 Token 不得打印到日志。
- RAG 入库优先使用异步任务，避免同步接口超时。
- 用户输入、检索内容和系统提示词要明确边界，降低 Prompt Injection 风险。
- AI 输出返回后，业务后端还要做结构校验和业务兜底。

## 8. 配置与环境变量

仓库只提交示例配置：

```text
application-local.example.yml
application-prod.example.yml
.env.example
config.example.yaml
```

要求：

- 示例配置使用 `${PLACEHOLDER}` 占位符。
- 本地真实配置文件加入 `.gitignore`。
- 生产配置通过环境变量、服务器私有配置文件或进程管理工具注入。
- 新增配置项必须同步更新对应 README、架构文档或中间件文档。
- 日志不得输出密码、Token、API Key、JWT、完整连接串。

## 9. 日志与异常

- 后端统一响应结构和错误码，详见 `doc/2.架构设计/2.3接口规范.md`。
- 每个请求日志携带 `traceId`。
- 业务异常用于可预期错误，例如参数非法、资源不存在、无权限。
- 系统异常统一兜底，返回克制的通用提示。
- AI 服务异常需要区分模型超时、模型限流、解析失败、检索失败。
- 生产日志必须脱敏。

## 10. 测试要求

后端：

- domain 层核心业务规则写单元测试，优先不依赖 Spring 容器。
- application 层用例编排、事务边界和权限协作写单元测试或切片测试。
- infrastructure 层 Mapper 复杂 SQL 写集成测试。
- interfaces 层登录、权限和接口错误码写接口测试。
- Flyway migration 必须能在空库完整执行。

前端：

- 核心工具函数写单元测试。
- 路由守卫、登录引导和关键表单流程至少人工验收。
- API 封装统一处理成功、失败、未登录和权限不足。

AI 服务：

- Pydantic schema 写解析测试。
- Prompt 输出结构写模拟测试或稳定性测试。
- RAG 检索流程写最小集成测试。
- 大模型不可用时验证降级结果。

## 11. 文档同步

以下变更必须同步更新文档：

- 新增或修改中间件依赖。
- 新增环境变量、配置字段、启动参数。
- 修改 API 路径、请求响应结构、错误码。
- 修改部署端口、启动顺序、健康检查地址。
- 修改核心架构边界，例如 AI 服务是否能访问业务库。

如果文档和代码冲突，应在同一次变更中修正，避免后续开发者按过期文档联调。

## Context

当前项目已完成 sprint202601 的前后端工程底座：后端提供统一响应、traceId、健康检查等基础能力，前端提供清新简约的 Vue 3 应用外壳、学习路线页面和若干占位页面。现阶段顶部“登录 / 注册”仍为占位，受保护能力尚未具备真实登录态，后端也尚未持久化用户数据。

sprint202602 的目标是在该底座上补齐用户注册登录与基础权限能力。该变更横跨后端、前端、数据库迁移、安全配置和中间件文档：后端需要接入 MySQL 与 Flyway 初始化用户表，使用 JWT 进行无状态认证；前端需要用 Pinia 管理 token 和当前用户，支持刷新后恢复登录态，并为热门面经、AI智能刷题、个人中心等入口提供统一登录引导。

## Goals / Non-Goals

**Goals:**
- 后端使用 MySQL 保存用户信息，并通过 Flyway 管理 `users` 表迁移脚本。
- 支持用户名、密码、昵称、邮箱注册，密码使用 BCrypt 或 Argon2 哈希保存。
- 支持用户名密码登录，成功后返回 Bearer JWT、过期时间和用户摘要。
- 支持 `/api/v1/users/me` 获取当前登录用户，响应中不得包含密码哈希。
- 支持 `/api/v1/auth/logout` 退出登录接口，前端清理 token 与用户信息。
- 前端支持登录注册弹窗、刷新恢复登录态、路由守卫、登录引导和个人中心基础页。
- 同步维护 MySQL 中间件文档，覆盖本地安装、启动、配置、验证和部署注意事项。

**Non-Goals:**
- 不实现 Redis token 黑名单、验证码、短信验证、邮件验证或第三方登录。
- 不实现头像上传、个人资料编辑、建议评论提交、题库、AI智能刷题和答题记录。
- 不新增单元测试代码，仅整理启动验证、接口联调和人工验收清单。
- 不在仓库内提交真实密码、Token、JWT 密钥、生产连接地址或其他敏感信息。

## Decisions

### 1. 使用 MySQL + Flyway 管理用户持久化

选择 MySQL 作为本期用户数据存储，Flyway 负责建表脚本版本化。用户表包含用户名、昵称、头像、邮箱、密码哈希、经验值、等级、段位、创建时间、更新时间和逻辑删除字段，并为用户名和邮箱建立唯一约束。

替代方案包括继续使用内存存储或文件存储。内存存储无法支撑刷新、重启和后续迭代复用；文件存储不适合并发和查询扩展。因此本期直接接入 MySQL，为后续评论、记录和用户成长体系提供统一数据基础。

### 2. 使用无状态 JWT 完成认证

登录和注册成功后由后端签发 JWT，前端通过 `Authorization: Bearer <token>` 访问受保护接口。token claims 至少包含用户 ID、用户名和过期时间，默认有效期为 7200 秒。JWT 密钥通过 `JWT_SECRET` 或本地私有配置提供，示例配置只允许使用占位符。

替代方案包括服务端 Session 或 Redis token 黑名单。Session 需要额外会话存储，不符合当前轻量迭代目标；Redis 黑名单适合强制下线和撤销 token，但本期明确不接入 Redis。因此退出登录采用前端清理 token、后端返回成功的无状态模式。

### 3. 后端按 auth、user、common/security 分层组织

认证接口、认证应用服务、用户领域模型、用户仓储和安全过滤器分包维护，避免将 JWT、密码校验、数据库访问和接口 DTO 混杂在控制器中。公共异常码沿用统一响应结构，认证失败返回 `AUTH_UNAUTHORIZED`，用户名或邮箱冲突返回 `RESOURCE_CONFLICT`。

替代方案是快速在单个控制器内完成所有逻辑。该方式实现快但可维护性差，不利于后续评论、刷题和用户成长体系复用当前用户能力，因此不采用。

### 4. 前端使用 Pinia + localStorage 管理登录态

前端 auth store 保存 `token`、`user`、`initialized`，localStorage key 固定为 `ai_learn_access_token`。应用启动或路由守卫触发时，如果存在 token 但缺少用户信息，则调用 `/users/me` 恢复登录态；恢复失败则清理本地 token 并展示登录引导。

替代方案是在组件内部自行读取 localStorage。该方式容易造成登录态分散和刷新恢复逻辑重复，无法统一处理 token 失效，因此采用集中式 store。

### 5. 受保护入口统一展示登录引导

热门面经、AI智能刷题和个人中心对游客展示“登录后即可使用该功能”引导，不直接进入空白页或产生接口错误。学习路线和建议评论区占位页继续允许游客访问。

替代方案是直接重定向到独立登录页。当前产品形态更适合弹窗式轻量登录注册，能减少页面跳转并保持清新简约的 UI 风格，因此本期采用登录引导弹窗与登录注册弹窗组合。

## Risks / Trade-offs

- [JWT 密钥配置不当导致安全风险] → 使用环境变量或本地私有配置注入，示例配置仅保留占位符，并在 MySQL/启动文档中说明不得提交真实密钥。
- [无状态退出无法立即让已签发 token 失效] → 本期接受该限制，控制 token 默认有效期；如后续需要强制下线，再引入 Redis 黑名单或 token 版本号机制。
- [邮箱唯一索引与可选邮箱可能存在数据库兼容细节] → 建表脚本允许邮箱为 NULL，并在应用层仅对非空邮箱执行格式与唯一性校验。
- [前端 token 过期后用户体验不一致] → `/users/me` 失败时统一清理登录态并展示登录引导，避免页面继续保留过期用户信息。
- [新增 MySQL 影响本地启动门槛] → 在 `doc/中间件/MySQL.md` 中提供安装、启动、配置、验证和部署说明，并在示例配置中使用占位符。

## Migration Plan

1. 增加后端 MySQL、Flyway 和持久化相关依赖，补充占位配置项。
2. 新增 Flyway 迁移脚本初始化 `users` 表，确保脚本可重复用于本地新库初始化。
3. 实现用户仓储、认证应用服务、密码哈希、JWT 签发解析和认证过滤能力。
4. 实现注册、登录、退出、当前用户接口，并接入统一响应和错误码。
5. 前端新增 auth/user API、auth store、登录注册弹窗、登录引导弹窗、路由守卫和个人中心页面。
6. 更新 `doc/中间件/MySQL.md` 与本地启动验证说明，使用占位符配置数据库连接和 JWT 密钥。
7. 人工验证注册、重复用户名、登录成功、密码错误、未登录 `/users/me`、登录后 `/users/me`、刷新恢复登录态、退出清理登录态和游客受保护入口引导。

回滚策略：若变更未发布生产，仅回退代码与迁移脚本即可；若已部署并执行迁移，回滚应用代码前需确认是否保留 `users` 表数据，必要时先备份用户表再执行人工回滚脚本。

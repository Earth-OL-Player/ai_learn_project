## 1.主问题：请介绍一下你们数据报表平台的整体链路。

我们这套链路主要服务于支付系统的交易报表：

首先，交易数据主要存储在 MySQL 的分库分表中。我们使用 Flink CDC 捕获 MySQL 的数据变更，通过预先配置好的同步任务和表名匹配规则，将交易数据同步到 Doris 的 ODS 原始数据层。

然后，我们使用 Airflow 编排 Python DAG，每天凌晨 `0:30` 触发数据加工任务。任务会基于交易时间的毫秒级时间戳，处理前一天的交易数据，依次完成以下数据分层：

- 从 ODS 清洗得到 DWD 明细层；
- 按代理商、商户、交易日期等维度汇总得到 DWS 汇总层；
- 最后通过Doris 物化视图构建ADS应用层数据。

后端服务不直接查询 MySQL，而是基于 ADS 层封装数据服务接口，为前端提供代理商日交易趋势、交易笔数和金额分布、交易成功率等报表能力。



### 1.1 你们的 CDC 是实时的，但 Airflow 每天凌晨才加工，这不是矛盾吗？

不矛盾，我们这套链路属于“**实时采集、离线加工、统一查询**”的模式。

Flink CDC 负责将 MySQL 的变更数据持续同步到 ODS，使 ODS 数据尽可能保持新鲜。

但业务报表主要是日报、趋势分析和统计类需求，对秒级实时性的要求没有那么高，因此 DWD、DWS 和 ADS 采用每天凌晨统一加工的方式。

这样设计主要有两个考虑：

第一，日报类指标一般按照自然日统计，统一批量加工更容易保证数据口径一致。

第二，今日实时报表依赖基于ODS层的同步物化视图，因此需要ODS层具有最新数据。



### 1.2具体是怎么处理迟到数据的？

对 CDC 延迟和 ODS 最大交易时间进行监控；

发现前一天数据仍在持续到达时，标记该日期为待校准状态；

对最近几天的数据进行滚动重算；

重算时按日期分区覆盖或使用幂等写入；

报表最终以校准后的数据为准。

当时项目主要通过凌晨任务前的延迟窗口解决常规延迟，极端迟到数据主要依赖人工核对和补数。



### 1.3Airflow 任务失败后重跑，会不会重复统计？

使用Doris的UNIQUE KEY数据模型，天然支持upsert。



### 1.4Flink CDC 如何保证数据不丢失和不重复？

Flink CDC 通过 Checkpoint 和状态恢复减少重复读取和数据丢失风险；Doris 侧再结合主键、版本字段或幂等写入，保证任务重启和重复投递时不会影响最终结果。



### 1.5Doris ODS 层使用什么表模型？

选择了 Doris Unique Key 模型，我们业务是交易报表，交易明细和交易汇总，都不能出现重复数据，否则会导致统计出错。选择Unique Key 的Upsert能力，刚好可以避免数据重复的情况。



### 1.6Doris 如何做分区和分桶？

分区主要根据数据的时间范围设计，我们按照交易日期进行按月分区。

分桶主要根据常用查询条件和数据分布选择，综合我们业务实际情况，我们根据代理商ID进行分桶。



### 1.7你简历中没有明确写 Hive、Spark、DataX，岗位又要求这些，你怎么回答？

当时我们的核心目标是支付报表的低延迟查询，而不是建设传统离线数仓。Doris 更适合直接承接分析查询和聚合报表，因此选择了 Flink CDC 加 Doris 的轻量方案。Hive 更适合离线数仓和批处理场景，如果后续平台需要沉淀大规模离线明细或统一湖仓体系，我会再评估 Hive、Spark 等组件。
